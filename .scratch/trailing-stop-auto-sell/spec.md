# Trailing Stop 자동 매도

Status: ready-for-agent

## Problem Statement

Trailing Stop은 지금 상태만 계산한다. 모의투자 환경에서 활성화·고점·Trailing Stop 트리거를 판정하고 계좌 확인의 Trailing Stop 보기에 보여 주지만, 트리거가 일어나도 매도 주문은 나가지 않는다. 사용자는 화면에서 "매도 조건 충족"을 보고 직접 팔아야 한다.

이제 판정 결과대로 실제로 팔고 싶다. 다만 자동 매도는 사용자의 최종 확인 없이 돈이 움직이는 일이므로, 다음이 지켜져야 한다.

- 실전투자에서는 절대 주문이 나가지 않는다.
- SL / TP와 같은 종목에서 겹쳐도 두 번 팔지 않는다.
- 팔리지 않았을 때 그 종목이 "매도 조건 충족"으로 영영 남지 않는다.
- 서버가 꺼진 사이 팔고 다시 산 종목이 예전 고점 때문에 곧바로 팔리지 않는다.
- 언제, 왜, 얼마나 팔렸는지(또는 왜 안 팔렸는지)를 화면과 Discord로 안다.

## Solution

모의투자 환경에서 **Trailing Stop 트리거**가 일어나면 그 종목의 **매도 가능 수량** 전량을 시장가로 파는 **자동 매도**를 낸다. 제외종목은 지금처럼 판정하지 않으므로 팔지 않는다. 자동 매도는 SL / TP가 쓰는 공용 자동 매도 규칙을 그대로 따른다. 투자 환경과 종목마다 진행 중인 자동 매도는 하나뿐이고, 서버가 접수 응답을 받은 자동 매도의 체결 알림에는 "Trailing Stop 자동 매도"가 붙는다.

트리거된 종목을 아직 보유하고 있으면, 켜진 Trailing Stop 세션이 새로 시작될 때마다(서버를 다시 시작한 때 포함) 그 세션의 첫 정규장 시세 체결에서 자동 매도를 한 번 더 낸다. 같은 세션 안에서는 다시 내지 않는다.

앱이 체결을 받지 못한 사이 평균 매입가가 바뀐 종목은 팔고 다시 산 것일 수 있으므로 활성화를 푼다.

계좌 확인의 Trailing Stop 보기에서 "매도 조건 충족"인 종목에는 자동 매도가 어디까지 왔는지(보내는 중 / 접수 / 실패 · 다음 세션에 다시 시도 / 다음 시세에서 매도 / 세션 밖 · 다음 세션에 매도)를 함께 보인다. Trailing Stop 설정 화면과 상태 보기의 "지금은 상태만 계산하고 팔지 않습니다" 안내는 실제로 판다는 안내로 바꾼다.

자동 매도를 따로 켜는 스위치는 없다. SL / TP처럼 Trailing Stop 세션을 켜는 것이 곧 그 세션에서 자동 매도를 허락하는 것이다.

## Implementation Decisions

**용어**

- `CONTEXT.md`의 **활성화**, **Trailing Stop 트리거**, **고점 기록**, **Trailing Stop 상태**, **자동 매도**를 이번 결정대로 넓혔다. "활성 세션"은 **활성화**와 헷갈리므로 쓰지 않고 **켜진 Trailing Stop 세션**이라고 쓴다. 코드, 로그, 화면 문구는 이 이름을 따른다.

**키움 TR**

- 새 TR은 없다. 매도는 SL / TP 자동 매도와 같은 경로(잔고를 다시 읽어 매도 가능 수량 전량을 시장가로 보내는 주문 서비스)를 쓴다. 국내 kt10001, 미국 ust20001이다.
- 시세와 체결은 지금처럼 공유 실시간 연결(ADR 0001)로 받는다.

**실전투자 차단**

- 새 스위치를 두지 않는다. Trailing Stop 감시는 모의투자 환경에만 만들고, 키움 client가 주문 허용이 꺼진 환경의 주문을 막는다(ADR 0003). 이 두 겹에 맡긴다.

**자동 매도 연결**

- Trailing Stop 감시는 공용 자동 매도(`AutoSell.sell`)를 부른다. 이름은 "Trailing Stop"으로 넘긴다. 그래서 다음은 바꾸지 않고 그대로 쓴다.
  - 투자 환경과 종목마다 진행 중인 자동 매도 하나(중복 주문 방지)
  - 접수된 주문번호 기억과 체결 알림의 "Trailing Stop 자동 매도" 표시
- 시세 처리는 주문 결과를 기다리지 않는다. 매도는 따로 돌리고, 트리거 때 만든 요청 ID를 주문 키, 로그, 체결 알림에 이어 쓴다. SL / TP와 같다.
- 체결 알림의 "Trailing Stop 자동 매도" 표시와 요청 ID 연결은 공용 자동 매도가 접수 응답으로 받은 주문번호에만 붙는다. 결과를 모르는 주문, 서버를 다시 시작한 뒤 온 체결, 주문 응답보다 기다리는 시간 넘게 먼저 온 체결에는 붙지 않는다. SL / TP와 같은 한계다.
- 자동 매도 결과는 그 매도를 시작한 세션 실행에 속한다. 앞 실행에서 시작한 매도의 결과가 새 실행이 시작된 뒤 나오면, 로그와 Discord 알림만 남기고 지금 실행의 시도 기록과 상태 API의 `auto_sell`은 바꾸지 않는다.
- SL / TP 코드와의 큰 중복 정리는 하지 않는다. 매도 보내기와 결과 알림 가운데 함께 쓸 수 있는 작은 부분만 함께 쓴다.

**언제 파는가**

- 감시는 세션 실행(켜진 Trailing Stop 세션이 그날 시작될 때마다 하나, 서버 시작 때도 새로 하나)마다 "이번 실행에서 자동 매도를 시도한 종목"을 둔다. 세션 기준만 바꾼 저장은 같은 실행이다.
- 시세 체결 한 건을 지금 규칙대로 판정한 뒤(제외종목, 대상 아님, 판정할 수 없는 가격, 정규장 밖, 보유종목 확인 중 등은 지금처럼 건너뜀):
  - 이 체결로 트리거가 일어났으면 자동 매도를 낸다.
  - 이미 트리거된 종목이고 이번 실행에서 아직 시도하지 않았으면 자동 매도를 낸다(다시 시도).
  - 어느 쪽이든 그 종목을 이번 실행의 시도한 종목에 넣는다. 결과와 상관없이 이번 실행에서는 다시 내지 않는다.
- 트리거된 종목도 지금처럼 시세를 구독한다. 그래야 다음 실행의 첫 시세 체결을 받는다.
- 보내기 직전 확인: 감시가 멈춤, 세션 실행이 바뀜, 제외종목이 됨, 기억이 지워짐(활성화가 풀림) 가운데 하나면 보내지 않는다(cancelled). 연결이 끊긴 것만으로는 막지 않는다. 끊기기 전 체결가는 실제 체결이었기 때문이다. SL / TP와 같다.
- 주문 직전 잔고 확인의 평균 매입가: 공용 자동 매도 경로에 선택 항목으로 "다시 읽은 보유종목 확인"을 더한다. 매도 가능 수량을 읽은 바로 뒤, 키움에 보내기 전에 부르며, 거절하면 보내지 않고 `cancelled`로 끝낸다. SL / TP는 넘기지 않아 동작이 그대로다. Trailing Stop은 여기서 다시 읽은 평균 매입가를 **평균 매입가 비교**와 같은 규칙으로 판단한다. 같으면 보낸다. 다르지만 인정되는 체결로 설명되면 새 값으로 바꾸고 보낸다. 설명되지 않으면 기억을 지우고(`purchase_price_changed`) 보내지 않는다. 트리거와 주문 사이에 연결이 끊긴 채 팔고 다시 산 새 보유분을 예전 트리거로 팔지 않으려는 것이다. 이미 키움에 보낸 주문은 취소하지 않는다.

**결과별 처리**

- 결과와 상관없이 같은 실행에서는 다시 내지 않는다. 새 실행에서 그 종목을 아직 보유하고 트리거 상태면 다시 낸다. 결과에 따라 규칙을 나누지 않는다.
  - 접수된 주문이 전량 체결되면 지금처럼 기억을 지우므로 다시 내지 않는다.
  - 접수됐지만 미체결 매도가 남아 있으면 매도 가능 수량이 0이라 보내지 않는다(`skipped`).
  - 일부만 체결되고 남았거나, 주문이 체결 없이 사라졌으면(장 마감 등) 다음 실행에서 남은 매도 가능 수량을 판다.
- 다시 시도할 때마다 잔고를 새로 읽어 매도 가능 수량만큼만 보낸다. 미체결 매도에 묶인 수량은 빠지므로, 결과를 몰랐던 주문이 사실 접수됐어도 두 번 팔리지 않는다.
- 결과는 메모리에만 둔다. 고점 기록 파일에는 적지 않는다. 재시작은 새 실행이라 어차피 다시 시도한다.

**평균 매입가 비교 (예전 고점 버리기)**

- 기억마다 마지막으로 확인한 평균 매입가를 둔다.
- 보유종목을 읽을 때마다, 기억이 있는 종목의 평균 매입가를 확인한 값과 비교한다.
  - 지난 확인 이후 그 종목의 내 계좌 체결을 받았으면 새 값으로 바꾼다(추가 매수, 일부 매도).
  - 단, 지난 확인 이후 체결 수신에 공백이 있었으면(서버 시작, 다시 연결, 체결 실시간 등록 거부) 다음 비교 한 번은 받은 체결을 인정하지 않는다. 공백 전에 받은 체결도, 공백 뒤 첫 비교 전에 받은 체결도 마찬가지다. 공백 동안 팔고 다시 샀을 수 있기 때문이다.
  - 받지 않았는데 값이 다르면 기억을 지운다. 로그 이유는 `purchase_price_changed`다. 이 종목은 활성화 대기부터 다시 판정한다.
  - 같으면 그대로 둔다.
- 평균 매입가는 활성화할 때 적으므로 모든 기억에 늘 있다.
- 주문 직전 잔고 확인에서도 같은 규칙으로 판단한다(언제 파는가).
- 체결과 다시 읽기가 엇갈려 잘못 지우더라도 고점만 잃을 뿐 잘못 팔리지는 않는다. 이 방향으로 받아들인다.
- 세션 밖에서 기억이 있는 종목의 체결을 받아 보유종목을 다시 읽을 때도 같은 비교를 한다.

**고점 기록 파일 (버전 2)**

- 종목마다 `purchase_price`(마지막으로 확인한 평균 매입가, 문자열 소수)를 더한다. 늘 값이 있다. 그 밖의 칸과 쓰기 규칙(임시 파일 뒤 바꿔치기, 고점 갱신은 5초에 한 번 묶어 쓰기, 활성화·트리거·삭제는 바로 쓰기)은 그대로다.
- `purchase_price`를 바꾸면 바로 쓴다. 트리거된 종목은 고점을 갱신하지 않아 다른 쓰기가 없으므로, 그대로 두면 재시작 뒤 앱이 봤던 변경을 못 본 변경으로 여겨 트리거 기억을 지우게 된다. 평균 매입가는 보유종목을 읽을 때만 바뀌어 쓰기가 잦지 않다.
- 버전 1 파일을 읽으면 기억을 모두 지우고 빈 버전 2로 바로 다시 쓴다. 상태만 계산하던 단계의 트리거로 배포 직후 팔지 않고, 평균 매입가를 확인할 수 없는 예전 고점이 배포 중 다시 산 보유분을 팔지 않게 하려는 것이다. 지운 종목코드를 로그(`trailing_stop_record_migrated`)로 남긴다. Discord로는 알리지 않는다.
- 버전 1도 2도 아니거나 형식이 맞지 않으면 지금처럼 `state_unreadable`로 판정을 멈춘다.

**자체 서버 API**

- `GET /api/environments/{environment}/trailing-stop/status`의 `stocks` 각 항목에 `auto_sell`을 더한다. 이번 세션 실행에서 그 종목의 자동 매도 시도이며, 시도하지 않았으면 `null`이다. 새 실행이 시작되면 모두 `null`로 돌아간다.

```json
"auto_sell": {
  "state": "accepted",
  "reason": null,
  "quantity": 10,
  "order_no": "0012345",
  "at": "2026-11-02T02:12:03+00:00"
}
```

  - `state`: `sending`(잔고 확인부터 주문 응답까지), `accepted`, `failed`
  - `reason`(`failed`일 때만): `rejected`, `unknown`, `in_progress`, `no_sellable`, `cancelled`
  - `at`: 결과가 나온 시각, `sending`이면 시작한 시각. UTC ISO 8601이다.
- 다른 칸과 응답 규칙은 바뀌지 않는다.

**화면**

- Trailing Stop 상태의 여섯 가지 이름은 그대로다. `triggered`인 종목에만 "자동 매도" 값을 다음 순서로 정해 보인다.
  1. 감시 중이 아니고 이유가 `no_session`이면 "세션 밖 · 다음 세션에 매도"
  2. 감시 중이 아니고 그 밖의 이유면 지금처럼 멈춘 이유(자동 매도 줄 없음)
  3. `auto_sell`이 `null`이면 "다음 시세에서 매도"
  4. `sending`이면 "보내는 중"
  5. `accepted`이면 "접수 · 주문번호 · 수량 · 시각"
  6. `failed`이면 "실패 · 다음 세션에 다시 시도 · <이유>"
- 이유 문구: 거부, 결과 확인 불가, 다른 자동 매도 진행 중, 매도 가능 수량 없음, 보내기 전 취소.
- 넓은 화면은 상세의 "자동 매도" 칸에 둔다. 좁은 화면 배지는 지금처럼 상태 이름만 보이고, 자동 매도 값은 펼친 상세에 둔다.
- 시각은 지금처럼 투자 환경의 시간대로 보이고, 오늘이 아니면 날짜를 붙인다.
- Trailing Stop 설정 화면의 안내와 상태 보기 위의 안내를 "매도 조건 충족이 되면 매도 가능 수량 전량을 시장가로 팝니다(모의투자만). 계좌 확인 화면의 Trailing Stop 보기에서 상태를 확인하세요."로 바꾼다. 상태 보기 위의 수익률·고점 안내는 그대로 둔다.

**Discord 알림**

- SL / TP 알림과 같은 모양으로, 결과가 `accepted`, `rejected`, `unknown`일 때만 보낸다. `in_progress`, `skipped`, `cancelled`는 로그만 남긴다.
  - "Trailing Stop 자동 매도 접수": 투자 환경, 종목(미국은 거래소 포함), Trailing Stop 세션, 트리거 체결가, 고점, 고점 대비 하락률(실제 값과 적용 기준), 활성화 수익률 기준, 평균 매입가, 수익률(수수료·세금 제외), 주문 수량, 주문번호, 다시 시도인지
  - "Trailing Stop 자동 매도 실패": 위 트리거 칸과 원인, 설명 "다음 Trailing Stop 세션에 다시 시도합니다."
  - "Trailing Stop 자동 매도 결과 확인 불가": 위 트리거 칸과 주문 수량, 설명 "접수 여부를 확인할 수 없습니다. 키움에서 주문 내역을 확인하세요."
- 색은 기존 관례를 따른다. 접수는 수익률이 0 이상이면 이익 색, 음수면 손실 색이다. 실패와 확인 불가는 회색이다.
- 다시 시도할 때 트리거 칸은 기억에 있는 트리거 시각·가격과 고점을 쓴다. 적용 기준은 지금 켜진 세션의 값이다.
- 트리거만으로는 알리지 않는다.

**로그**

- 이벤트: `trailing_stop_auto_sell_started`(code, attempt=`trigger`|`retry`, run), `trailing_stop_auto_sell_finished`(outcome, quantity, order_no, cause), `trailing_stop_send_refused`(reason), `trailing_stop_notified`, `trailing_stop_memory_forgotten`(reason=`purchase_price_changed` 추가), `trailing_stop_record_migrated`(cleared_codes).
- 트리거 때 만든 요청 ID를 자동 매도, 주문 키, 체결 알림까지 이어 쓴다. 다시 시도는 새 요청 ID를 만든다.

## Testing Decisions

- 좋은 테스트는 바깥에서 보이는 동작만 확인한다. 서버는 키움으로 나간 요청, HTTP 응답, Discord 메시지, 데이터 폴더의 파일로 확인한다. 화면은 사용자가 보는 글자로 확인한다. 감시 내부 클래스와 메서드는 직접 부르지 않는다.
- **서버 (pytest)**: 지금 Trailing Stop 감시 테스트와 SL / TP 자동 매도 테스트처럼 가짜 키움, 가짜 실시간 연결, 가짜 Discord, 고정 시계, 임시 데이터 폴더로 실제 앱을 띄운다. 새 테스트 자리는 만들지 않는다.
  - Trailing Stop 감시 테스트의 "모든 테스트에서 주문 TR 0건" 자동 확인은 뺀다. 대신 테스트마다 나간 주문 TR의 횟수와 내용(종목, 수량, 시장가, 미국 거래소)을 확인한다. 가짜 키움은 주문 응답을 준다.
  - 트리거 때 매도 가능 수량 전량 시장가 매도(국내·미국), 같은 실행에서 다시 내지 않음
  - 결과별: 접수 / 거부 / 결과 모름 / 매도 가능 수량 0 / 다른 자동 매도 진행 중 / 보내기 전 취소. 결과와 상관없이 같은 실행에서는 한 번만 내고, 아직 보유 중이면 다음 실행(다음 세션, 다음 날, 재시작)의 첫 정규장 시세 체결에서 한 번 더 냄. 접수 뒤 미체결이 남으면 매도 가능 수량 0으로 보내지 않고, 체결 없이 사라지면 다음 실행에서 팖
  - 주문 직전 잔고의 평균 매입가가 설명되지 않게 바뀌었으면 주문 TR이 나가지 않고 기억이 지워짐, 같거나 인정되는 체결로 설명되면 주문이 나감
  - 접수 뒤 일부만 체결되고 남으면 다음 실행에서 남은 수량을 팜
  - 세션 기준만 바꿔 저장해도 같은 실행이라 다시 시도하지 않음
  - 보내기 직전 확인: 세션 끝, 제외종목 추가, 기억 삭제, 감시 멈춤이면 주문이 나가지 않음
  - SL / TP와 같은 종목: SL / TP 진행 중이면 Trailing Stop은 보내지 않고 알림 없음, SL / TP가 다 팔았으면 매도 가능 수량 0
  - 평균 매입가: 체결을 받지 않았는데 바뀌면 기억을 지우고 팔지 않음(서버가 꺼진 사이 팔고 다시 산 경우를 재시작으로 재현), 체결을 받고 바뀌면 유지, 다시 연결 뒤 첫 비교 전에 받은 체결로는 인정하지 않음
  - 버전 1 고점 기록: 기억이 모두 지워지고 빈 버전 2로 다시 쓰이며, 배포 직후 시세에 매도가 나가지 않음
  - 실전 환경: 트리거 조건의 시세가 와도 주문 TR 0건
  - Discord: 접수·실패·확인 불가 알림의 제목과 칸, 체결 알림의 "Trailing Stop 자동 매도"
  - 상태 API의 `auto_sell` 값(보내는 중, 접수, 실패와 이유, 새 실행에서 `null`)
  - 로그에 자동 매도 시작·결과가 요청 ID와 필수 칸을 담음

  - 좁은 화면 배지는 상태 이름만, 상세에 자동 매도 값
  - 설정 화면과 상태 보기의 바뀐 안내 문구
  - 기존 Trailing Stop·계좌 e2e가 모두 통과함
- 기존 테스트, lint, 타입 검사, 화면 빌드, e2e가 모두 통과해야 한다.

## Further Notes

- 모의투자 확인(ready-for-human 티켓으로 둔다): 국내·미국 모의에서 실제 Trailing Stop 자동 매도 접수, 체결 알림의 "Trailing Stop 자동 매도" 표시(주문 응답과 체결 이벤트의 주문번호 형식이 같은지), 같은 종목을 SL / TP(그룹 2)와 Trailing Stop에 함께 시세 등록해도 거부 없이 두 기능 모두 시세를 받는지. 200종목 한도를 서로 다른 종목 수로 세는지 그룹별 등록 수의 합으로 세는지는 개인 모의계좌로 경계를 시험할 수 없어 미확인으로 남긴다.
- 보내기 직전 확인에 보유종목 확인 중(`holdings_pending`)을 넣지 않는다. 이 상태는 어느 종목이든 계좌 체결 하나로 켜지므로, 장 시작 때 여러 종목이 함께 트리거되면 첫 매도의 체결이 나머지 매도를 모두 취소한다. 잔고 확인 뒤 앱 밖에서 같은 종목을 팔았다면, 전량이면 매도 체결로 기억이 지워져 "기억 삭제"로 막히고, 일부면 키움이 매도 가능 수량을 넘는 주문을 거부해 다음 세션에 다시 시도한다.
- 체결 알림 표시는 서버가 접수 응답을 받은 자동 매도에만 붙는다. 결과를 모르는 주문과 재시작 뒤 체결에는 빠진다(자동 매도 연결 참고).
- 거래정지처럼 계속 거부되는 종목은 세션마다 실패 알림이 온다. 직접 팔거나 제외종목에 넣으면 멈춘다. 받아들였다.
- 알려진 한계(그대로): 다시 읽은 보유종목에 이미 반영된 매도 체결이 그 뒤에 들어오면 수량을 두 번 빼서 기억을 일찍 버릴 수 있다. 일찍 버리면 고점을 잃을 뿐 잘못 팔리지는 않는다.
- 서버가 꺼진 사이 팔고 같은 평균 매입가로 다시 산 경우는 알아낼 수 없다. 드물어서 받아들였다.
- 다음 날 시가가 고점 대비 하락률보다 낮게 시작하면 장 시작 첫 시세 체결에서 시장가로 팔린다. 다른 시스템과 같은 동작이다.

- Q12 평균 매입가 비교: 보유종목을 읽을 때마다, 지난 확인 이후 그 종목 체결이 없었는데 바뀌면 지움.
