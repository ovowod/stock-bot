# 키움 호출 간격 맞추기

Status: ready-for-agent

## Problem Statement

모의투자에서 계좌 확인, 매도 최종 확인, 순위 화면이 가끔 "키움 API 호출 한도를 넘었습니다"로 실패한다. 로그(2026-10-05~08)에는 `1700`이 100번 넘게 남았다. 모두 같은 인증정보로 **같은 TR**을 1초 안에 다시 부른 경우다. 서로 다른 TR은 몇 ms 간격으로 이어 불러도 통과했다.

- 국내 `ka00001`(계좌번호 확인) 22번: 계좌 확인, 보유 수량 확인, 매도 직전 잔고 재확인이 매번 부른다.
- 미국 순위 TR(`usa20910`, `usa01980`, `usa20540`, `usa20530`) 41번.
- 미국 `ust21070`(잔고) 12번: 계좌 확인 직후 매도 잔고 재확인이 겹쳐 "잔고를 확인하지 못해 주문하지 않았습니다"가 났다.
- `au10001`(토큰 발급): 앱 재시작 직후 1초 안에 다시 발급하다 막혔다.

지금은 기능마다 따로 막는다. 종목 검색은 1초를 기다리고, 순위는 lock으로 한 번에 하나씩 부른다. 나머지는 막히면 그대로 429를 돌려준다.

## Solution

키움에 요청을 보내는 단 한 곳(키움 클라이언트)에서, **같은 인증정보로 같은 TR**을 부를 때 앞 요청과 최소 1초 간격을 둔다. 간격이 모자라면 실패시키지 않고 기다렸다가 보낸다. 기다릴 시간이 5초를 넘으면 보내지 않고 지금과 같은 **호출 한도** 오류를 돌려준다. 모든 투자 환경과 주문에 같은 규칙을 쓴다.

계좌번호 확인(`ka00001`)은 토큰마다 한 번만 한다. 어느 계좌를 조회할지는 토큰이 정하기 때문이다.

종목 검색의 1초 대기와 순위 lock은 이 규칙으로 대신하고 없앤다.

## User Stories

1. As a 투자자, I want 계좌 확인 직후 매도 최종 확인을 열어도 잔고 재확인이 호출 한도로 실패하지 않기를, so that 매도를 다시 시도하지 않아도 된다.
2. As a 투자자, I want 새로고침을 연달아 눌러도 대부분의 조회가 조금 늦게라도 성공하기를, so that "잠시 후 다시 시도"를 보는 일이 줄어든다.
3. As a 투자자, I want 순위 화면의 카드 4개가 한꺼번에 조회되기를, so that 화면이 더 빨리 채워진다.
4. As a 투자자, I want 요청이 너무 많이 몰려 5초 넘게 기다려야 하면 지금처럼 "잠시 후 다시 시도" 안내를 보기를, so that 화면이 끝없이 로딩 중이지 않다.
5. As a 투자자, I want 주문이 호출 한도로 거부되어도 자동으로 다시 나가지 않기를, so that 같은 주문이 두 번 나가지 않는다.
6. As a 투자자, I want 보유종목이 여러 페이지여도 다음 페이지가 호출 한도로 실패하지 않기를, so that 계좌 확인이 페이지 수만큼 조금 늦더라도 성공한다.
7. As a 개발자, I want 요청이 간격 때문에 기다리거나 거부될 때 투자 환경, TR, 기다린 시간이 로그에 남기를, so that 느려진 이유와 거부된 이유를 로그로 찾는다.

## Implementation Decisions

**간격 맞추기 (키움 클라이언트)**

- 기준 단위는 (인증정보 묶음, TR)이다. 인증정보 묶음은 토큰 캐시와 같은 `credential_prefix`다. 국내 실전과 미국 실전은 인증정보가 같으므로 한 묶음이다. 키움이 한도를 앱 키별로 세는지는 문서로 확인하지 못했고, 그렇다고 가정한다.
- 같은 단위의 요청은 앞 요청을 보낸 시각에서 최소 1초 뒤에 보낸다. 먼저 온 요청이 먼저 나간다.
- 요청이 줄에 들어올 때 보낼 시각을 정하고, 지금부터 5초를 넘게 기다려야 하면 보내지 않고 기존 호출 한도 오류(`rate_limited`, 같은 안내 문구)를 돌려준다. 이렇게 거부된 요청은 보낼 시각을 차지하지 않는다.
- 5초 판단은 줄에 들어올 때 한 번만 한다. 차례가 온 요청은 실제 마지막 전송 시각을 다시 보고, 1초가 안 됐으면 더 기다린 뒤 보낸다. 그 때문에 5초를 조금 넘겨도 거부하지 않는다.
- 연속조회 다음 페이지(`cont-yn=Y`)도 새 요청과 똑같이 줄을 서고 1초 간격을 지킨다. 다음 페이지도 한도에 세어진다(Implementation Notes 2026-10-10).
- 이 규칙은 조회, 주문, 주문 취소, 토큰 발급(`au10001`)에 모두 적용된다. `8005` 뒤 새 토큰으로 다시 보내는 요청도 새 요청으로 보고 간격을 지킨다.
- 간격 맞추기의 거부는 키움의 호출 한도 오류와 똑같이 `rate_limited`로 분류된다. 그 오류를 감싸는 기존 경로(매도 전 잔고 재확인 502 `sellable_check_failed`, 취소 전 미체결 재확인 502 `open_orders_check_failed`)는 지금 동작을 그대로 따른다.
- 실전과 모의의 간격 값은 같다. 실전과 모의의 한도가 다르다는 근거가 없다.
- 호출 한도 오류(`1700`/`1701`/`1702`)를 받은 뒤 자동으로 다시 보내지 않는다. 지금처럼 429로 분류한다. 이 앱 말고 같은 인증정보를 쓰는 프로그램은 없다고 가정한다.
- 전체 한도(`1701`)와 그룹 한도(`1702`)에 대한 별도 제한은 두지 않는다. 지금까지 한 번도 나지 않았고 숫자도 모른다.
- 기록은 메모리에만 둔다. 앱이 재시작되면 사라지므로, 재시작 직후의 호출은 막지 못한다.
- 로그
  - 기다리면 `kiwoom_pacing_wait`(api_id, wait_ms)를 남긴다.
  - 5초를 넘어 거부하면 `kiwoom_pacing_rejected`(api_id, wait_ms)를 WARNING으로 남긴다.
  - 둘 다 요청 ID와 투자 환경이 함께 남는다.

**계좌번호 확인을 토큰마다 한 번**

- 계좌 확인은 지금 접근 토큰으로 `ka00001` 확인에 성공했으면, 같은 토큰을 쓰는 동안 다시 부르지 않고 확인한 계좌번호를 쓴다.
- 토큰이 바뀌면(만료, `8005`, 재시작) 다시 확인한다.
- 계좌번호가 다르면(409 `account_mismatch`) 기억하지 않는다. 다음 요청도 다시 확인한다.
- 확인 결과는 호출 전에 읽은 토큰에 기억한다. 확인 도중 토큰이 바뀌었으면 다음 요청이 새 토큰으로 한 번 더 확인한다. 같은 인증정보의 토큰은 같은 계좌를 가리키므로 안전한 쪽으로 틀린다.
- 첫 요청 여러 개가 동시에 들어와 각자 확인하는 것은 허용한다. 결과가 같고, 간격 맞추기로 한도에도 걸리지 않는다.
- 확인을 건너뛰면 `account_check_skipped` 로그를 남긴다. 로그만으로 `ka00001`을 건너뛰었는지 알 수 있게 한다.

**기존 대응 정리**

- 종목 검색의 두 국내 목록 호출 사이 1초 대기(`DOMESTIC_LIST_INTERVAL_SECONDS`)를 없앤다. 두 호출 모두 `ka10099`라서 공통 규칙이 같은 간격을 둔다.
- 순위의 lock을 없앤다. 서로 다른 순위 TR은 동시에 나가고, 같은 순위 TR은 1초 간격으로 나간다.
- 순위 화면은 네 카드의 요청을 동시에 시작한다. 지금은 앞 카드의 응답을 기다린 뒤 다음 카드를 요청한다. 카드별 성공·실패 표시와 오래된 응답 무시는 그대로 둔다.
- 순위 spec(`.scratch/ranking/spec.md`)의 "한 번에 하나씩" 규칙들(서버 잠금, 화면의 카드 순차 조회와 그 검증 항목) 아래에 이 spec으로 바뀌었다는 메모를 남긴다.

## Testing Decisions

- 좋은 테스트는 바깥에서 보이는 동작만 검증한다. 가짜 키움에 실제로 나간 요청의 순서와 시각, 그리고 자체 API의 응답을 본다. 키움 서버는 호출하지 않는다.
- 실제로 1초를 기다리면 테스트가 느려진다. 그래서 키움 클라이언트가 시각과 대기를 바꿔 끼울 수 있게 하고, 간격 테스트는 가짜 시계로 검증한다. 간격을 다루지 않는 기존 테스트는 기다리지 않게 둔다.
- 검증할 것
  - 같은 인증정보, 같은 TR의 두 요청은 1초 간격으로 나간다.
  - 다른 TR, 또는 다른 인증정보(국내 모의와 미국 모의)의 같은 TR은 기다리지 않는다.
  - 국내 실전과 미국 실전은 같은 단위로 센다.
  - 몰린 요청은 온 순서대로 나간다.
  - 5초를 넘겨야 하는 요청은 키움에 나가지 않고 `rate_limited`(계좌 확인 같은 일반 조회 API는 429)이며, 뒤 요청의 보낼 시각을 밀지 않는다.
  - 연속조회 다음 페이지도 1초 간격으로 나간다.
  - 연속조회 다음 페이지에서 `8005`가 나 다시 보내는 요청은 1초 간격을 지킨다.
  - 주문(`call_once`)도 간격을 지키고, 호출 한도 오류를 받으면 다시 보내지 않는다.
  - 대기와 거부 로그가 남는다.
  - 같은 토큰으로 계좌 확인을 두 번 하면 `ka00001`은 한 번만 나간다. 토큰이 바뀌면 다시 나가고, 계좌번호가 다르면 매번 다시 확인한다. 확인 도중 `8005`로 토큰이 바뀌면 다음 요청이 다시 확인한다.
  - 순위: 서로 다른 순위 TR은 동시에 나간다. 지금의 "한 번에 하나씩" 테스트를 바꾼다.
  - 순위 화면(Playwright): 네 카드 요청이 앞 응답을 기다리지 않고 나가고, 카드별 성공·실패가 따로 보인다. 지금의 "카드가 한 번에 하나씩 요청된다" e2e를 바꾼다.
  - 종목 검색: 두 `ka10099` 호출 사이 간격은 공통 규칙으로 지켜진다.

## Out of Scope

- 전체 한도·그룹 한도에 대한 별도 제한.
- 호출 한도 오류를 받은 뒤 자동 재시도.
- 앱 재시작을 넘어 호출 기록을 보존하는 것.
- 화면 쪽 요청 줄이기(계좌와 미체결을 한 요청으로 합치기 등).
- 실시간(WebSocket) 등록 수 제한.

## Further Notes

- 키움 문서에는 한도 숫자가 없다. 오류 메시지 세 가지(`1700` TR별, `1701` 전체, `1702` 그룹)만 있다. 1초는 로그에서 본 동작과 비공식 자료("TR 하나당 초당 1회 정도가 안전")를 근거로 정했다. 키움 GitHub 예제의 주석에는 `au10001`이 초당 약 2회라는 실측값이 있다.
- 한도를 계좌, 시장, 시간대별로 센다는 근거는 찾지 못했다.
- 문서로 확인하지 못한 것: 한도를 세는 단위(앱 키, 계좌, IP), 실전 한도, `1702`의 그룹 구성.

## Implementation Notes

### 2026-10-10: 연속조회 다음 페이지도 한도에 걸림
- 미국 모의 계좌 확인에서 `ust21070` 1페이지를 보낸 지 0.4초 뒤에 보낸 2페이지가 `1700`(유량=1, API ID=ust21070)으로 거부됐다. 예전에 0.18초 뒤의 다음 페이지가 통과한 것은 우연으로 본다.
- 그래서 다음 페이지를 기다리지 않던 예외를 없애고 모든 요청이 같은 줄을 서게 했다. 줄 중간에 다음 페이지가 끼어드는 경우와 `8005` 재전송의 예외 규칙도 함께 필요 없어졌다.
- 보유종목이 여러 페이지면 페이지마다 최대 1초씩 늦어진다.

### 2026-10-10: 계좌 확인 체감 속도
- 미국 모의 계좌 확인은 평균 약 1.7초 걸렸고, 그중 간격 맞추기는 약 0.5초, 나머지는 키움 응답 시간이었다.
- 계좌 API를 영역별로 나누지 않는다. 요약과 보유종목이 같은 잔고 TR에서 오므로, 나누면 같은 TR을 두 번 불러 오히려 느려지고 영역별 숫자의 시점이 어긋난다.
- 대신 화면은 투자 환경별로 마지막 계좌 확인 결과를 로그인 세션 동안 기억해, 다른 메뉴에 갔다 돌아오면 바로 보여주고 뒤에서 다시 불러온다.
- 서버는 잔고·예수금·종목 목록처럼 서로 다른 조회를 함께 보낸다.

- ✏️ 계좌번호 확인의 동시 요청·토큰 교체: 확인 작업 공유 대신, 호출 전에 읽은 토큰에 기억하고 동시 첫 요청의 중복 확인은 허용했다. 같은 인증정보의 토큰은 같은 계좌를 가리켜 틀려도 다시 확인할 뿐이다.
- ✅ 429 요구와 주문 전 확인 오류 처리의 충돌: 거부는 키움 클라이언트에서 `rate_limited`로 분류하고, 감싸는 기존 경로(매도·취소 전 재확인 502)는 그대로 둔다고 적었다.
- ✅ 모의투자 확인 절차의 재현성: 새로고침 연타 대신 스크립트로 조회 TR을 동시 7회 부르고 결과를 판정하는 절차로 03을 바꿨다.
